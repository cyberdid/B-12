# Аналіз master brief

Документ дає цілісний задум B-12 та достатній матеріал для початку специфікації. Найцінніше — безперервність досвіду, змінність LLM, розмежування рефлексів і міркування, українська як обов’язкова вимога та простежувані рішення. Поточна тека була порожньою: імпорт підтверджує наявність знань, але не реалізацію описаних функцій.

## Що можна використовувати вже

**Оновлення після імпорту:** [власний тест Bolt](bolt-first-test.md) на RTX 4060 підтвердив працездатність text-only моделі та коротку warm latency. Ризик Nano TTFT у початковому brief залишається відкритим: інше обладнання не тестувалося. Нове спостереження — context overflow може видаляти інструкції; його додано як Q18.

- [Задум](../topics/vision.md) задає продуктову рамку й відділяє компаньйона від набору голосових команд.
- [System 1/2](../topics/architecture.md) дозволяє зберегти interrupt і моторику незалежними від LLM latency.
- [Пам’ять з provenance](../topics/memory.md) дає спосіб перевіряти пригадування та історію перегляду поглядів.
- [Software-only шлях](roadmap.md) дозволяє перевірити ядро до вибору фізичної платформи.
- [Каталог джерел](../sources/master-brief.md) зберігає альтернативи; згадка технології не зобов’язує включати її у v1.

| Пріоритет | Розрив | Наслідок | Наступний доказ |
|---|---|---|---|
| P0 | Старий memory kernel і логи відсутні локально | Неможливо чесно продовжувати як готову реалізацію | Знайти repo/path, revision, schema, tests; або явно почати новий PoC |
| P0 | Append-only / «ніколи не стирати» суперечить забуттю | Можлива прихована копія приватного змісту | Політика життєвого циклу та перевірка видалення всіх похідних |
| P0 | Спостереження → short-term log до consent filter | Тимчасовий durable log може вже порушити вимогу | Визначити volatile/durable boundary до першого запису |
| P1 | Болт на Nano: перевірений vendor TTFT 5,785 с при 3K input проти цілі voice <1,5 с | Ця конфігурація не проходить бюджет | Власний short/cached prompt A/B та можливий host split |
| P1 | Показане спільне demo не дорівнює профілю повного стеку | Не доведено запас RAM і стабільність аудіо | Joint profiling з ASR/TTS, unified memory і dropout traces |
| P1 | Wireless media path не перевірено нами | Можливий блокер full-duplex і barge-in | Тривалий audio-only transport test без LLM |
| P1 | UA quality та ліцензії кандидатів не перевірені в цьому імпорті | Стек може не відповідати мовній вимозі | UA/EN corpus, TTS listening test, pinned model/runtime license inventory |
| P2 | Невизначені пороги доречності й точний latency SLO | Демонстрації складно порівнювати | Версійовані сценарії, rubric, перцентиль і кількість повторів |

TTFT і end-to-end audio вимірюють різні етапи: наведена невідповідність стосується саме опублікованої конфігурації, а не всіх можливих режимів Bolt. NVIDIA demonstration підтверджено як опис авторів; наша відтворюваність і сумарний RAM budget залишаються відкритими. [Межі незалежної перевірки](../sources/external-checks.md).

## Уточнення для проєктування

**Пам’ять.** Відділити незмінність аудиторської історії від зберігання персонального payload. Виправлення фактів можна дописувати подіями, але відкликання згоди вимагає окремої процедури очищення. Не переносити правило незмінності `raw/` у runtime без аналізу приватності.

**Контроль дій.** Identity, consent і authorization — різні контракти. Висока схожість голосу не надає права виконувати інструмент; текст про consent не стає сигналом контрольного каналу. Необхідні перевірювані негативні сценарії.

**Розподілення.** Для варіанта ноутбук + Jetson визначити, де authoritative пам’ять, що працює без ноутбука і що відбувається після втрати мережі. Фраза local-first сама не вирішує доступність 24/7.

**Навчання.** Спершу оцінювати накопичення досвіду та процедур. Fine-tuning ваг — окремий напрям з власними даними й критеріями, не автоматичний зміст «поступового розвитку».

## Рекомендований критичний шлях

1. Встановити походження старого коду й доступний персональний host; завершити контракти та policy boundary.
2. Відтворити мінімальний текстовий цикл: дозволена подія → пам’ять → evidence-based recall → одна контрольована дія → outcome → стан після restart.
3. Порівняти моделі на однакових UA/EN сценаріях і зафіксувати cold/warm TTFT.
4. Додати desktop PTT і змістовне streaming audio; потім AEC/barge-in.
5. Перевірити Wireless transport, робот і спільне навантаження Jetson за доступності обладнання.
6. Оцінювати довгі спогади, quiet mode та ініціативу на реальних часових інтервалах.

Це рекомендація порядку робіт, а не дозвіл автоматично почати всі етапи реалізації. Перший поточний крок і блокери — у [статусі](status.md), докази виходу з етапів — у [дорожній карті](roadmap.md).
