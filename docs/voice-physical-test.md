# Голос B-12: стан AEC і сценарій фізичного тесту

Цей документ розділяє три типи результатів: **синтетичні** (лінійний луна-канал без кімнати
й шуму), **фізичні** (реальний мікрофон і динамік) і **не виконано**. Синтетичні числа — верхня
межа для AEC і захист від регресій; вони не є акустичним результатом.

## 1. Стан AEC (станом на 2026-11-03)

### Що змінено

- **Референс.** Раніше весь TTS-буфер фрази подавався на початку відтворення. Тепер `AudioPlayer`
  подає його блоками в момент запису в програвач (`tts.py`, `_feed_reference`). FIFO референсу
  споживається з тією самою швидкістю, що й кадри захоплення; нестача заповнюється нулями.
- **Затримка.** Оцінюється кросс-кореляцією історії мікрофона з історією споживаного референсу до
  400 мс (раніше 16 мс). Серед майже рівних піків (через періодичність голосу) береться найближчий
  до попередньої оцінки.
- **Фільтр.** Розв'язання систем 256×256 на кожному кадрі займало ~590 мс на цій збірці NumPy, що
  неприйнятно для кадру 32 мс. Замінено на блоковий NLMS: ~0,6 мс на кадр (P95 2,3 мс, максимум
  4,9 мс; вимірювання синтетичні, на CPU цього ноутбука).
- **Подвійне мовлення.** Фільтр заморожується, як і раніше. Синтетичний тест підтверджує, що голос
  користувача збережено.

### Синтетичні результати (верхня межа, не фізика)

| Сценарій | Результат | Джерело |
|---|---|---|
| Затримка 40, 200, 350 мс, шумовий референс | оцінка точна: 640, 3200, 5600 семплів | `tests/unit/test_aec_quality.py` |
| Ехо, шумовий референс | ERLE ~80 дБ | експеримент, 6 с |
| Ехо, періодичний голосоподібний тон, затримка 200 мс | ERLE ~48 дБ; тест вимагає >25 дБ | `test_periodic_voice_like_echo_is_still_cancelled` |
| Подвійне мовлення (користувач говорить поверх B-12) | кореляція виходу з голосом користувача 0,96; рівень 0,94 від оригіналу | експеримент |
| Залишкове відлуння під час подвійного мовлення | ERLE 9,7 дБ (фільтр заморожено) | експеримент |

**Обмеження синтетики.** Лінійний канал без відлуння кімнати, без шуму, без дрейфу годинників
пристроїв. Тон має періодичність, через яку оцінка затримки неоднозначна на кратних періоду
(наприклад, 0 мс інколи дає 1707 семплів). Тому тести затримки використовують шумовий референс.

### Що не виконано

- **Фізичних вимірювань немає.** Ні ERLE, ні затримки, ні помилкових спрацювань VAD на реальному
  мікрофоні й динаміку ще не було.
- **Хвіст відлуння.** Фільтр має 256 відводів (16 мс). Відлуння кімнати триває 100–300 мс, тож
  власний AEC не компенсує його. Для реального шляху призначений системний echo-cancel PipeWire
  (варіант B нижче).
- **Дрейф годинників.** Пристрої вводу й виводу мають різні годинники. Оцінка затримки з
  ковзним вікном має відстежувати дрейф, але на реальному обладнанні цього не перевірено.

## 2. Два варіанти для фізичного тесту

**Варіант A — власний AEC (за замовчуванням).** Нічого не змінювати в системі. Очікувано слабкий
на реальному відлунні; саме його і треба виміряти.

**Варіант B — системний echo-cancel PipeWire (WebRTC AEC3 всередині PipeWire).** Модуль
`libpipewire-module-echo-cancel.so` встановлено на цій машині, `pactl` немає. Його завантаження
змінює граф аудіо, тому **не виконано і не запускалось**; це рішення власника. Шаблон, який
треба перевірити перед запуском:

```
pw-cli load-module libpipewire-module-echo-cancel \
  '{ aec.method = webrtc source.props = { node.name = "b12-aec-source" }
     sink.props = { node.name = "b12-aec-sink" } }'
# відкат: pw-cli unload-module <id із виводу load-module>
```

Після завантаження B-12 мав би захоплювати `b12-aec-source` і відтворювати в `b12-aec-sink`.
Ці імена ще не підключено до коду; це окремий крок, якщо варіант B буде обрано.

## 3. Сценарій фізичного end-to-end тесту

**Умови.** Ноутбук із внутрішнім мікрофоном і динаміком (на цій машині це sof-hda-dsp). Тиха
кімната. Власник присутній, гучність обрана так, щоб не було дискомфорту. Власнику потрібно
знати, що B-12 говоритиме вголос.

**Перевірка перед запуском** (тільки читання):

```
b12 voice status              # uk_tts_ready, en_tts_ready, vad_backend, devices
b12 voice unmute
b12 doctor
```

**Запуск.** Події пишуться у файл (по одному JSON на рядок):

```
b12 voice live | tee ~/b12-voice-$(date +%Y%m%d-%H%M).jsonl
```

Зупинка: Ctrl-C. Підсумок `stats` (utterances, asr_calls, barge_ins) друкується останнім рядком.

**Сценарії.** Кожен записати окремо, з позначкою часу початку.

1. **B-12 говорить, користувач мовчить.** Попросити розповісти довгу відповідь (наприклад,
   «розкажи про погоду в Києві коротко»). Очікувано: `aec` події з високим `erle_db` і
   `echo_dominant: true`; жодного `barge_in` і жодного `utterance` від власного голосу B-12.
2. **Користувач перебиває B-12.** Посередині відповіді сказати «стоп, інше питання». Очікувано:
   `barge_in` з `stop_ms`; перша відповідь завершується `turn` зі станом `cancelled`; друга репліка
   розпізнається один раз (`asr_calls` дорівнює числу `utterance`).
3. **Обидва говорять одночасно.** Користувач говорить поверх відповіді без перебивання. Фіксувати
   `double_talk` у `aec` подіях і чи не втрачено репліку користувача (`transcript`).
4. **Стороннє аудіо.** Увімкнути музику або відео на низькій гучності поза B-12. Фіксувати
   хибні `utterance` і `barge_in`.
5. **Зміна гучності.** Під час відповіді змінити гучність динаміка вдвічі. Фіксувати `erle_db`
   до і після зміни.

**Що фіксувати на кожному сценарії.** Файл JSONL, час початку й кінця, сказане голосом,
відповідь B-12 і спостереження (чи чути відлуння, чи B-12 перебив сам себе).

**Пропоновані критерії приймання** (поріг треба погодити з власником перед тестом; це не
результати):

- `erle_db` у сценарії 1: медіана не менша за 15 дБ.
- Хибні `barge_in` у сценарії 1: 0 за хвилину тиші.
- Сценарій 2: `stop_ms` медіана менша за 50 мс; відповідь завершується `cancelled`.
- Сценарій 3: репліку користувача розпізнано (`transcript` містить сказане).

**Межі вимірювань.** `stop_ms` у `barge_in` — це час надсилання сигналу зупинки процесу
відтворення, а не момент фізичної зупинки звуку. Фізична зупинка потребує петлі мікрофона на
той самий динамік; такого вимірювання в цьому сценарії немає. `erle_db` в подіях — онлайн-оцінка
за RMS, а не еталонне вимірювання; для точного ERLE треба записувати сирий мікрофон і референс.

## 4. Що лишилось до фізичного приймання

1. Запустити сценарії 1–5 на цій машині з явним дозволом власника.
2. Вирішити: варіант A чи варіант B за результатами сценарію 1.
3. Для точного ERLE і затримки додати запис сирих сигналів (мікрофон і референс) у файл.
