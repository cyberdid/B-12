\begin{abstract}
A previous report described B-12, a local-first agent runtime, and Capri, its desktop companion. This follow-up asks what an evaluation of such a system actually measures. We ran a 92-scenario suite (80 runnable on the available hardware) through the companion's own runtime inside a filesystem sandbox, instead of calling the language model directly. The first evaluation, which bypassed the runtime, scored 27 of 80 and produced a privacy leak that the harness itself had created; the same suite run through the runtime scored 39 of 80 before any change to the companion. Auditing the benchmark exposed further measurement errors: an incorrect reference value that failed two models for a correct answer, a symbolic-link test whose fixture was an ordinary text file, and scenarios that typed marker strings instead of exercising the mechanism they named. With these corrected, three repeated runs of each configuration gave 49, 49 and 48 passes for the primary 4-billion-parameter model (Nemotron Bolt E4B with Gemma 4 12B for swappable scenarios), 45, 43 and 47 for Gemma 4 26B (mixture of experts) and 45, 45 and 42 for Gemma 4 31B. Totals hid the noise: between two identical runs, three to ten scenario verdicts changed. Seventeen scenarios failed in every run of every configuration, which locates the main limits in the system and the benchmark rather than in model scale. Two interventions illustrate how small prompt decisions dominate a small model's behaviour. A single explicit brevity sentence halved conversational reply length but also halved tool use on work turns (18 to 9 of 21). Moving recalled memories from the system text to a message after the user's turn let the inference server reuse its prompt cache, cutting median time to first token from 0.99 to 0.74 seconds with no detectable change in behaviour. All results come from one laptop and an author-built benchmark; we report them as an engineering case study with raw data.
\end{abstract}
\noindent\textbf{Keywords:} local-first agents; AI companion; agent evaluation; benchmark validity; run-to-run variance; prompt caching; instruction following; small language models

\section{Introduction}
Evaluating a conversational agent is usually framed as evaluating a model. For a deployed companion this framing is incomplete. What the owner experiences is the result of a runtime that decides who is speaking, which memories are recalled, which tools are visible, which actions need approval and how the request is laid out for the model. A benchmark that bypasses that runtime measures a different system; a benchmark that contains its own errors measures the benchmark. Even a sound benchmark run once can mislead, because a stochastic agent run twice under identical conditions does not return identical verdicts.

This paper continues an earlier report on B-12 and Capri \cite{capriprev,b12}. That report described the architecture and historical measurements. Here we study the measurement itself, over three days of iterative evaluation on a single laptop. We pose four questions:

\textbf{RQ1 (harness validity):} how much does a result depend on whether scenarios pass through the agent's runtime, and how often is the benchmark rather than the agent at fault?
\textbf{RQ2 (noise):} how large is run-to-run variance at the level of individual scenarios, and what does it imply for comparisons?
\textbf{RQ3 (model scale):} does a larger local model improve a companion whose runtime, prompt and tools are held fixed?
\textbf{RQ4 (prompt decisions):} how do single, local changes to the prompt affect a small model's behaviour and latency?

The contributions are empirical and methodological rather than algorithmic. We document a set of concrete measurement failures and their corrections; repeated-run statistics for three model configurations; a controlled A/B experiment showing that a brevity instruction suppresses tool use in a small model; and a prompt-layout change that improves latency through cache reuse while leaving behaviour unchanged within the resolution of the suite. Every number in the paper is computed by a script from artifacts published in the project repository (\cref{sec:availability}).

\section{Background and Related Work}\label{sec:related}
\paragraph{Agent evaluation.} Holistic and agent benchmarks such as HELM and AgentBench measure models across many tasks \cite{helm,agentbench}. They typically evaluate a model behind a benchmark-specific scaffold. Our setting is the reverse: the scaffold is the product, and the model is a replaceable component. Memory-centred agents \cite{memgpt,generative} make the same point architecturally: behaviour depends on what the surrounding system places into the context. Long-context studies show that where information sits in a prompt affects its use \cite{lost}.

\paragraph{Instructions, constraints and tools.} Performance degrades as the number of simultaneous instructions grows \cite{multiply}. Decomposing and checking multi-constraint instructions improves compliance \cite{decrim}. Tool use under explicit constraints remains difficult even for large models \cite{cctu}. Length can be controlled with dedicated methods rather than plain instructions \cite{ruler}. Our brevity experiment (\cref{sec:brevity}) sits at the intersection of these findings for a 4-billion-parameter local model.

\paragraph{Evidence, preferences, initiative and model change.} Detecting conflicts between pieces of evidence is an open problem \cite{econ,conflictweb}. Preference-following benchmarks show that models often fail to apply stated user preferences \cite{prefeval,botherme,benchpres}. Proactive agents must decide when to speak, not only what to say \cite{proactive,chimein}. Agents may drift in identity across conversations and across model transitions \cite{drift,transition}. Several of the failing scenarios in our suite test exactly these capabilities; we return to them in \cref{sec:discussion}.

\section{System and Method}\label{sec:method}
\subsection{System under test}
B-12 is a Python runtime with a FastAPI control plane, SQLite stores for control state, sessions and memory, a tool registry and an agent loop; Capri is its persona and desktop client \cite{capriprev}. Models are served by Ollama 0.33.3 \cite{ollama}. Each request is admitted against an explicit tokenizer and chat-template profile and an 8192-token context. Identity, consent and tool permissions come from a control channel; text produced by the model never grants a capability. During the period studied the runtime gained several fixes found by the evaluation itself (\cref{sec:validity}); the repeated runs use the corrected code.

\subsection{Scenario suite}
The suite contains 92 scenarios in 11 groups: autobiographical memory, long-term continuity, cross-model behaviour, reasoning, security, autonomy, human interaction, voice, reliability, robotics and multi-session journeys. Twelve require a microphone, speaker or robot and are reported as blocked, leaving 80 runnable. Of all scenarios, 66 are answered by the pinned primary model, 10 by a swappable model and 16 need no model. Expectations are deterministic checks: required or forbidden substrings, regular expressions, tool calls, Cyrillic script share, reply length and latency bounds. Seventeen scenarios are measured by live handlers that exercise real components (scheduler, disk reserve, signal handling, reflection, deletion) instead of a single chat turn.

\subsection{Runtime-faithful harness}
\Cref{fig:harness} contrasts the two harnesses used. The original harness sent the model one prompt written by the benchmark, containing every memory of the scenario regardless of which actor owned it. The runtime-faithful harness instead creates a fresh state directory per scenario, creates actors with their owner and consent flags, writes memories into each actor's own namespace at the scenario's dates, and answers each turn with the runtime's agent loop under the grant the API would issue. Nothing is approved on the scenario's behalf. Because tools act on a real filesystem, the suite runs inside a bubblewrap sandbox with a read-only root and empty home, temporary and media directories.

\subsection{Statistics}
We report passes out of 80 runnable scenarios with Wilson intervals \cite{wilson}. Pooling three runs triples the number of verdicts but not the number of scenarios, so pooled intervals understate scenario-level uncertainty; we therefore also report per-run counts, the number of scenarios that pass in all runs (stable pass) or none (stable fail), and pairwise discordance: the number of scenarios whose verdict differs between two runs. For paired comparisons of the same scenarios under two conditions we use a sign test on scenarios whose pass count changed, which is the exact form of McNemar's test \cite{mcnemar}. Latency is time to first token (TTFT) measured by the runtime, with the prompt tokens the server reports as evaluated and as reused from its cache.

\section{Results}\label{sec:results}
\subsection{Harness and benchmark validity (RQ1)}\label{sec:validity}
The first evaluation used the original harness and passed 27 of 80 runnable scenarios. Investigating one failure, a guest learning the owner's secret, showed that the leak was produced by the harness: it had placed the owner's memories into the prompt it wrote for the guest. Run through the runtime with otherwise unchanged code, the suite passed 39 of 80. Subsequent changes, each found by a failing scenario and each covered by a unit or integration test, brought single runs to 47 and, after merging the desktop branch and fixing the regressions it introduced, to 48.

A manual review of the remaining failures, done by the evaluating agent and checked against raw replies, classified 31 failures as follows: 19 genuine behavioural defects, 8 replies that were correct in substance but missed the expected wording, and 4 scenarios that did not match the system's design. \Cref{tab:defects} lists the measurement defects we corrected or reinterpreted. The most instructive is RE-06, which asks for the sample standard deviation of five numbers. Its reference answer was wrong; two of the four models had answered correctly and were marked as failing.

We did not relax expectations after seeing results. Where a live handler replaced a marker scenario, its criteria are fixed in code; one of them (AUT-06) still fails in some runs because the generated reflection names the I\textsuperscript{2}C bus but not the power interference that the criterion requires.

\subsection{Run-to-run noise (RQ2)}\label{sec:noise}
\Cref{tab:repeats} summarises three runs of each configuration and \cref{fig:repeats} shows each run. For the primary configuration the totals were 49, 49 and 48, a standard deviation below one scenario. The stability of the total is misleading. Between runs one and two four verdicts changed, and between either of them and run three seven changed; flips in both directions cancelled in the sum. Nine scenarios were unstable. For the 26B model, pairwise discordance was 4, 8 and 6; for the 31B model 4, 5 and 3.

The practical consequence is that a difference of two or three scenarios between two single runs carries little information. Our own earlier statement that ``one to three verdicts change between identical runs'' confused the difference of totals with discordance; a parallel review of the raw data corrected it.

\subsection{Model scale (RQ3)}\label{sec:scale}
In single runs two days earlier, the primary configuration passed 48, Gemma 4 12B with semantic recall 43, Gemma 4 26B 41 and Gemma 4 31B 43. Repeated runs preserved the ordering between the primary configuration and the two larger models (means 48.7, 45.0 and 44.0). Restricting the comparison to the 68 model-dependent scenarios, the primary configuration passed 38, 38 and 37, the 26B model 34, 32 and 36, and the 31B model 34, 34 and 31.

Two confounds limit this comparison. First, the larger models ran on a different host with semantic recall, whose embedding bridge started slowly on the cloud CPU; several of their failures (LT-02, JOURNEY-04, MEM-01) had correct content and missed only latency bounds. Second, the primary configuration is itself mixed: ten scenarios use Gemma 4 12B. The defensible conclusion is therefore negative: within this runtime and suite, moving from a 4-billion-parameter model to models of 26 and 31 billion parameters did not improve the outcome.

Seventeen scenarios failed in every run of all three repeated configurations (AUT-07, CM-01, INT-01, INT-06, INT-07, INT-08, JOURNEY-01, JOURNEY-03, LT-08, MEM-03, MEM-04, MEM-07, REL-08, SEC-04, SEC-06, SEC-08, VOI-02). They include an unimplemented feature (proactive mention of an unresolved issue), persona verbosity, latency bounds and keyword checks of refusals that were correct in substance. None of these is likely to be solved by a larger model alone. Qualitatively, in the single runs the 26B model was the most careful with tools: where the smaller models sometimes described system state without checking it, it called the system-information and process tools and read the relevant files.

\subsection{A brevity sentence suppresses tool use (RQ4)}\label{sec:brevity}
Capri's persona asks for laconic everyday replies, yet replies to greetings or expressions of fatigue often ran to several hundred characters. We tested an explicit rule in a controlled A/B experiment. The control persona contains the sentence ``be laconic in everyday talk; give complex and technical answers precisely and completely''. The treatment replaces it with ``answer greetings, questions about yourself, tiredness or emotions in one to three short sentences (up to about 300 characters), without lists or headings; give complex and technical answers, reports and analysis precisely and completely''. Everything else (code, model, scenarios, seeds and grants) was identical. Seventeen scenarios, ten conversational and seven requiring tools or memory, ran three times under each arm with the primary model on an idle GPU.

\begin{figure}[tbp]\centering\input{figures/brevity.tex}
\caption{Brevity A/B with the primary model, three repeats per arm. (a) Characters per conversational reply. (b) Work turns in which the model called at least one tool.}\label{fig:brevity}\end{figure}

\Cref{fig:brevity} shows the result. The rule did what it said: the median conversational reply fell from 188 to 97 characters and the mean from 337 to 118. It also did something it did not say. On work turns, the share of turns in which the model called a tool fell from 18 of 21 to 9 of 21. In a diagnostic task that requires reading two files (RE-01) the model stopped reading them; in a request to delete ``test files'' (INT-04) it stopped listing the directory first, which turned three passes into none; in a system-status request (AUT-02) it answered without calling the status tools. Scenario passes fell from 22 to 18 of 51. A previous, unrepeated observation of the model switching to Russian under the same rule did not recur in these 102 executions; no reply had a Cyrillic share below one half.

The effect is consistent with reports that compliance degrades as simultaneous instructions accumulate \cite{multiply,decrim} and that constraints interact poorly with tool use \cite{cctu}. Our data cannot identify the mechanism, but they show that in a small model an instruction about the form of a reply can change whether the model performs work at all. A rephrased rule stating that brevity applies to text and not to work did not restore tool use in an earlier, unrepeated check. We therefore did not adopt the rule.

\subsection{Prompt layout and the prompt cache (RQ4)}\label{sec:cache}
The runtime recalls memories relevant to each turn and passes them to the model as untrusted evidence. They had been appended to the system text. The Gemma 4 chat template renders the system text, then the tool schemas, then the conversation. Because recalled memories change almost every turn, the longest prefix shared with the previous request ended where the memories began, before 17 tool schemas and the whole history. Ollama 0.33.3 reports reused prompt tokens \cite{ollama}, which made this measurable.

We moved the evidence into a separate system message placed directly after the current user message and restricted the validator to accept a system message only there and only with the evidence header. \Cref{fig:cache} and \cref{tab:cache} compare three sessions of seven turns each, with eight seeded memories and a different memory asked about in each turn, on an idle GPU. The median number of cached tokens rose from 1404 to 2009, prefill time fell from 0.32 to 0.07 seconds and median TTFT from 0.99 to 0.74 seconds; the slowest warm turn fell from 1.11 to 0.82 seconds. The template renders a system message after a user turn, and in a direct check the model answered from such a message.

To check that behaviour did not change, the full suite ran three more times with the new layout (\cref{tab:repeats}): 52, 48 and 48 passes against 49, 49 and 48. Six scenarios passed more often and six less often; the sign test gives $p=1.0$. Two shifts were systematic. MEM-07, in which the owner reports a move to a new city, went from zero to three passes: the new fact now sits next to the question. MEM-01 went from three passes to none: with the evidence next to the question, the model answered directly instead of calling the memory-search tool the scenario requires, and copied the internal date prefix (\texttt{[2026-10-24]}) into its reply. A one-sentence rule asking for dates in words fixed the prefix in three of three checks; the missing tool call remains a scenario expectation that the reply does not need.

\section{Discussion}\label{sec:discussion}
\paragraph{Measure the system that users meet.} The largest single change in the reported score, from 27 to 39 of 80, came from routing scenarios through the runtime rather than from improving the companion. A benchmark that writes its own prompt can both hide defects and create failures that do not exist. For agents whose behaviour depends on recall, permissions and persona, a runtime-faithful harness is a precondition for meaningful numbers.

\paragraph{Audit the benchmark as well as the agent.} Seven of the corrections in \cref{tab:defects} concerned the measurement. A wrong reference value failed the models that were right; keyword checks rejected correct refusals. A manual review of failures is cheap relative to the cost of optimising an agent against a defective target, and it should precede any prompt change motivated by a score.

\paragraph{Report discordance, not only totals.} Three to ten verdicts changed between identical runs. Comparisons of agent versions or models should be paired by scenario and repeated, and claims of improvement should survive a paired test. A stable total is not evidence of a stable system.

\paragraph{Small models make prompt decisions expensive.} A single sentence about reply length halved tool use. The safer design is to separate decisions the model makes poorly under competing instructions from those it must make: a deterministic router could apply a length budget only to plainly social turns after any work is finished, rather than asking the model to trade off form and work in one prompt. The literature on multi-constraint following points in the same direction \cite{multiply,decrim,cctu}.

\paragraph{Prompt layout is a performance parameter.} Moving one block of the prompt reduced TTFT by a quarter without changing behaviour. Placing stable content first and volatile content late is a general rule for any server that reuses a prompt prefix; the reported count of cached tokens makes compliance testable.

\paragraph{Scale is not the bottleneck here.} The scenarios that fail everywhere test persona brevity, latency, initiative, preference use and conflict reporting. Benchmarks for preferences \cite{prefeval,botherme,benchpres}, initiative \cite{proactive,chimein} and evidence conflicts \cite{econ,conflictweb} suggest that these need explicit state and policy around the model. For a companion intended to survive model replacement, behavioural continuity across models remains untested: our configurations differ in more than the model, and a controlled same-state migration test is future work \cite{transition,drift}.

\section{Threats to Validity}\label{sec:threats}
\textbf{Single host and author-built suite.} All local results come from one laptop; the suite was written by the project and checked by the same agent that ran it. No independent replication exists. \textbf{Deterministic checks.} Substring and pattern checks underestimate correct behaviour; the manual review was performed by one reviewer. \textbf{Few repeats.} Three runs per configuration show the size of the noise but do not support fine-grained comparisons. \textbf{Confounded model comparison.} The larger models differ in host, recall mode and, for latency, in bridge start-up time; the primary configuration mixes two models. The Gemma 4 12B tag in the public library has since received new weights, so the 12B results apply to the local revision only. \textbf{Small A/B experiments.} The brevity experiment uses 17 scenarios and three repeats per arm; the cache measurement uses three sessions of seven turns with the primary model only. Effects of this size are unlikely to be artefacts, but their magnitude on other models and hardware is unknown. \textbf{Moving code.} The runtime changed during the study; each result is tied to the commit stated in the data package.

\section{Conclusion}
Evaluating a local companion through its own runtime, auditing the benchmark, and repeating runs changed the picture more than any model swap. With a corrected harness and suite, a 4-billion-parameter model in a carefully built runtime was not outperformed by 26- and 31-billion-parameter models. Its behaviour, however, proved sensitive to single prompt decisions: one sentence about length suppressed tool use, while one change of layout made replies start a quarter sooner at no behavioural cost. We suggest that evaluations of personal agents report the harness, the benchmark corrections and scenario-level discordance alongside any headline score.
